Laya 是一个 Decision Model：用一次前向计算处理选择、评分和是非问题。我把它的推理路径移植到了 JAX，做成了 deciax，让这类模型可以在 TPU 上运行，再用 Pallas 优化其中的计算。

这次测试里1，单芯片 TPU v6e 的英文模型单问题调用 p50 是 2.18 ms，多语言模型是 1.55 ms。作为对比，A100 SXM4、H100 PCIe、H200 NVL 的最快实测结果分别是 6.4 / 4.0 ms、4.8 / 3.2 ms、5.8 / 4.1 ms（英文 / 多语言）。

每次 50 个问题时，v6e Pallas 的 p50 是 33.69 / 17.83 ms，相较普通 JAX 实现提速约 2.3 倍；A100、H100、H200 的最快实测结果分别是 68.8 / 36.2 ms、44.0 / 23.2 ms、39.8 / 21.2 ms。

# 从一个例子开始

deciax 接收输入和一组问题，返回结构化结果。以一条重复扣款的工单为例：

import deciax

decider = deciax.load("laya")
result = decider.decide(
    {"user": "I was charged twice this month. Please refund the duplicate."},
    {
        "department": {
            "type": "choice",
            "instructions": "Which department should handle this?",
            "criteria": {
                "billing": "payments, invoices, refunds",
                "technical": "bugs, outages, system errors",
                "other": "everything else",
            },
        },
        "urgency": {
            "type": "score",
            "instructions": "How urgent is this?",
            "criteria": ["not urgent", "soon", "blocking"],
        },
        "refund_requested": {
            "type": "noul",
            "instructions": "Does the user ask for a refund?",
        },
    },
)
print(result)

# 我们先用 JAX 实现 Laya

我们先用 JAX 重新实现 Laya 的推理计算：由 ModernBERT encoder 处理输入，再由决策 head 输出各个问题的结果。输入构造保持不变，checkpoint 和 tokenizer 也沿用原模型。这样就得到了一条可以在 TPU 上运行的普通 JAX 推理路径，作为下面性能测试和后续 Pallas 优化的基线。

## JAX 实现的性能如何？

测试在 Oct 12, 2026 进行，覆盖 RTX 3090、A100 SXM4、RTX A6000、H100 PCIe 和 H200 NVL，以及各用一颗芯片的 TPU v5e、v6e。

延迟图展示进程内调用的稳态 p502，包含输入编码、推理和结果处理。实心柱是 p50，虚线标记 p95。

先只看 GPU 的 PyTorch eager 和 TPU 的普通 JAX 实现：

英文模型单问题调用，GPU eager 的 p50 是 13.3–25.8 ms，v6e JAX 是 2.27 ms。但每次 50 个问题时，v6e JAX 需要 76.79 ms，GPU eager 的最低值是 H200 NVL 的 57.5 ms。多语言模型也有类似变化：v6e JAX 从单问题的 1.61 ms 增长到 50 问题的 41.24 ms，H200 eager 的 50 问题结果是 34.0 ms。

## 耗时分解

接着拆开基线调用的耗时，以英文模型为例3：

单问题的 GPU eager 调用包含大量小 kernel：英文模型一次调用就有 1090–1213 次 cudaLaunchKernel。设备执行之外的余量很大，优化需要同时考虑 kernel 融合和调用开销。

每次 50 个问题时，计算本身开始占主要时间。v6e JAX 的英文模型总延迟为 76.79 ms，其中单独测量的 forward-only 是 71.27 ms，输入编码约 3 ms。XProf 中，dot_general 和 sub 分别占这组设备时间的约 38% 和 21%，提示我们关注矩阵计算和逐元素操作的数据搬运。

# 如果让它更快呢？

我们使用 Pallas 对 TPU 上的 Laya 进行 kernel fusion 优化。当序列长度不超过 512 token 时，每个 encoder 层和 Transformer head 层都由一个 kernel 完成，将归一化、投影、attention 和 MLP 融合起来，encoder 中还包括 RoPE4。中间结果留在片上 VMEM 中，减少反复读写 HBM；每个 kernel 的权重也驻留在 VMEM 中，供不同的行块复用。此外，我们调整了 attention 的矩阵布局，采用转置形式的计算来更好地适配 TPU 矩阵单元。PR #1 记录了这些优化，以及长序列使用的三 kernel 路径。

为了尽可能公平，我们也测试了使用 TileLang、CUDA Graph 和 torch.compile 优化的 GPU 版 Laya。对于每台主机、每个模型和问题数，我们选取实测最快的实现，与 TPU v6e 上的 Pallas 版本进行比较。

单问题调用，v6e Pallas 的英文模型 p50 是 2.18 ms，多语言模型是 1.55 ms。GPU 的英文模型最低值是 H100 PCIe 上 torch.compile with cudagraph 的 4.8 ms，多语言模型最低值是 3.2 ms。这个形状下，Pallas 相比普通 JAX 的改善很小。

每次 50 个问题，v6e 的英文模型从 JAX 的 76.79 ms 降到 Pallas 的 33.69 ms，多语言模型从 41.24 ms 降到 17.83 ms，分别提速 2.28 倍、2.31 倍。英文模型的 forward-only 从 71.27 ms 降到 28.25 ms，多语言模型从 36.54 ms 降到 13.36 ms。

# 不同 batch size 下的性能

Batch size 会影响硬件利用率，因为它决定了硬件能同时处理多少计算。小 batch 可能无法充分利用计算单元，调度等固定开销在单次调用中的占比也更高。增大 batch 可以提供更多并行工作，让权重在更多输入之间复用，并将固定开销分摊到更多决策上。但它也会增加计算量和内存需求，因此吞吐量提高的同时，单次调用的延迟也可能变长。在小 batch 下表现好的实现，换到大 batch 后不一定仍有同样的优势。

Laya 会把每个问题构造成独立的一行输入，因此这里针对同一条输入，每次分别提交 1、5、10、50 个问题，改变逻辑 batch size。TPU 实现会将这些行补齐到支持的 batch 桶，所以问题数代表有效输入行数，不一定等于实际执行张量的 batch 维度。下图对比 H100、H200 与 v6e Pallas 在这些 batch size 下的单次调用延迟，观察处理更多决策时耗时如何增长：

# 部署模型服务

## HTTP 服务

为了让其他应用调用 Laya，我们通过 deciax.serve 将同样的决策接口暴露为 HTTP 服务：向 POST /v1/systemone 发送输入和问题，服务以 JSON 返回结构化答案。模型在服务启动时加载，并在后续请求之间复用。

在已安装 deciax 的 TPU 主机上，运行以下命令，使用 Pallas 实现在 8000 端口启动 HTTP server：

python -m deciax.serve --model laya --impl pallas --port 8000

启动和预热完成后，在另一个终端发送请求：

curl http://127.0.0.1:8000/v1/systemone \
  -H 'Content-Type: application/json' \
  -d '{
    "state": "I was charged twice. Please refund the duplicate charge.",
    "questions": {
      "refund": {
        "type": "noul",
        "instructions": "Does the user ask for a refund?"
      }
    }
  }'

返回结果中的 answers.refund.noul 表示答案为真的概率，同时还包含置信度、action probability 和 token 用量。服务也提供 GET /health 健康检查和 POST /v1/systemone/batch 批量接口。

在 loopback、keep-alive 条件下，我们测得 v6e Pallas 的单问题 HTTP p50 为英文 3.0 ms、多语言 2.4 ms。

# 总结

deciax 把 Laya 的结构化决策能力带到了 TPU 上。这次实验中，普通 JAX 已经能把单问题调用做到约 2 ms，Pallas 在这个形状下的额外收益很小；当每次调用增加到 50 个问题，融合后的 Pallas 路径相较普通 JAX 提速约 2.3 倍。问题数改变了主要开销，也改变了优化的收益。

在本文测试的输入、模型和实现范围内，v6e Pallas 的单问题和 50 问题延迟都低于参与对比的 GPU 实现。

如果你想试试 deciax，可以在 Colab 中体验，也可以到 GitHub 仓库查看代码。
