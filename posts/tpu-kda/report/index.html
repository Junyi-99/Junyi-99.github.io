## 在 TPU 上加速 Kimi K3 KDA：从 VPU Execution 到 MXU-Optimized Kernels

# 1. 引言

Kimi K3 为 Kimi Delta Attention（KDA）引入了一项重要的 algorithm–system co-design：通过将 decay term 限制为 lower_bound = -5，并采用 subblock_size = 16，K3 约束了 chunk-local computation 的 numerical range，使关键 matrix operations 能够以 BF16 高效执行。这一设计让 KDA 更适合 matrix accelerators。

在 GPU 上，FlashKDA 利用这一结构，将 KDA 的关键部分重新表述为可在 Tensor Cores 上执行的小型 dense matrix operations。然而，SGLang-JAX 目前缺少能够在 TPU 上利用同一机会、专门面向 Kimi K3 的 KDA prefill kernel。现有实现仍将大量计算留在 TPU vector units 上，未能有效利用 MXU。

在这项工作中，我们分两个阶段为 TPU 实现高效的 Kimi K3 KDA prefill。

首先，我们移植 FlashKDA 使用的 matrix-based computation strategy，并将主要 compute path 重新表述为 MXU-friendly operations。仅这一转换，相比现有 SGLang-JAX 实现带来 2.28× speedup（固定形状）/ 2.48×（ShareGPT length distribution）。

其次，消融差值归因表明（§5、§11），仅仅把计算迁移到 MXU 还不够。一旦主要 arithmetic 得到加速，之前处于次要地位的成本——包括 fragmented computation、layout transformations、intermediate materialization 和 pipeline stalls——就会成为主要瓶颈。因此，我们通过 computation restructuring、kernel fusion、layout optimization 和 pipelining 重新设计 kernel structure。

相较于初始 MXU 实现，这些优化进一步带来 5.6× speedup（固定形状累计）；相较于原始 TPU 实现，整体达到 12.8×（固定形状）/ 18.4×（ShareGPT distribution）。[JUNYI: 此为关键数据，需要二次核对]

本文全部 latency 数字为 median：switch-ladder 采用 warmup 5 / repeat 20，roofline 复测集采用 warmup 20 / repeat 100（两组一致，±2% 内）。固定形状（headline）指 T=8192（4×2048 varlen packed）、H=16、K=V=128、BT=64、BF16。

我们不对 cached prefix length（P）做 sweep。对 KDA kernel 而言，cached prefix 的全部历史压缩在定长 recurrent state [H, 128, 128] 中：P 只决定 initial_state 的内容，不改变 kernel 的任何计算量、访存量或指令流，因此不在本 kernel 评估范围内。

# 2. Kimi K3 为何改变了 Hardware Opportunity

KDA 既包含 recurrent state updates，也包含 chunk-local computations。高效实现这些 operations 的一个主要困难在于 numerical stability：累计 decay terms 可能跨越很大的 dynamic range，使直接采用 low-precision matrix formulations 并不安全。

Kimi K3 通过限制 decay term $g_t \geq -5$ 改变了这一设计，并以 $C = 16$ 的 subblocks 处理 tokens。

因此，在一个 16-token subblock 内，累计 decay range 是有界的。[JUNYI: 在这里引用一下 Kimi K3 的 Technical report]

这一 numerical constraint 使 KDA 能够分解为规则的 matrix operations。代表性 operations 的 shapes 包括

$$16 \times 128 ; @ ; 128 \times 16$$

以及每个 chunk 内的小型 $16\times16$ matrix operations。

由此得到的 computation 非常适合 matrix-multiply hardware。在 GPU 上，这一结构可以映射到 MMA/Tensor Core operations；TPU 则通过 Matrix Multiply Unit（MXU）提供了类似机会。

[图 1：Algorithm-to-hardware mapping。] 建议流程： KDA recurrence → bounded decay + 16-token subblock → BF16-safe chunk formulation → dense matrix operations → Tensor Core / TPU MXU 该图应在展示任何 performance result 之前，先确立这项工作的核心前提。

# 3. 现有 TPU Path 仍有大量 Performance 未被利用

虽然 Kimi K3 暴露了 matrix-friendly computation，但现有 SGLang-JAX KDA prefill path 没有对 Kimi K3 进行适配。

现有实现位于 python/sgl_jax/srt/kernels/kda/kda.py（main 分支），chunk_kda_fwd 按 4-stage 执行：gate cumsum（pallas_kda_gate_cumsum）→ intra-chunk（kda_fwd_intra：elementwise 衰减张量构造 + 逐行前向消元求解 (I+L)⁻¹）→ 跨 chunk 递推（chunk_gated_delta_rule_fwd_h）→ 输出（chunk_kda_fwd_o_gk）。其中衰减张量构造与逐行消元均为 element-wise / 行串行操作，由 VPU 执行，未触碰 MXU。

# 4. 阶段 1：向 MXU 暴露 KDA Matrix Parallelism

我们的第一项优化是将 FlashKDA 使用的 matrix computation strategy 移植到 TPU。

我们不再主要通过 vector-oriented computation 执行相关 KDA operations，而是将 chunk-local computation 重新组织为适合 TPU MXUs 的显式 matrix multiplications。

其中包括如下形式的代表性 GEMMs：

$$16 \times 128 ; @ ; 128 \times 16$$

具体而言，被替换的 operation 有两个：

  1. 衰减张量 Aqk/L 构造（原：elementwise 构造 [BT,BT] 衰减矩阵，VPU）→ 以每个 SB=16 子块的中点为参考点做精确分解，变为 strip-GEMM： q̃[16,128] @ k̃ᵀ[128,16]（bf16 输入，fp32 累加），沿 BT=64 共 4 个子块条带。 数值安全性由指数预算保证：(SB/2)·|lower_bound|/ln2 = 8×5/0.693 ≈ 57.7 < 126 （bf16 指数上限），这正是 K3 的 lower_bound=-5 + SB=16 设计所开启的空间。
  2. (I+L)⁻¹ 求解（原：逐行前向消元，行串行，VPU）→ 有限 Neumann 因子链 (I−L)(I+L²)(I+L⁴)… 直接作用于 RHS 拼接矩阵 [I | βv | βk·2^G] （[64, 64+128+128]，bf16 单 pass，不物化显式逆），全部为 [64,64] @ [64,·] 小 GEMM。选择"因子链乘 RHS"而非"先求逆再乘"的原因是精度：后者 bf16 下 max|err| 6.9e-4 超出 5e-4 oracle 门限，前者 2.77e-4 通过（见 §13）。

方法论源自 MoonshotAI/FlashKDA（有限 Neumann 级数 + 低精度单 pass）；TPU 形态差异： bf16 取代 fp16，块尺寸取 MXU 友好的 BT=64 而非 FlashKDA 的 C=16（后者服务 fp16 数值范围与 GPU SM 占用，见附录 A）。

# 5. 使用 MXU 是必要条件，但还不够

将主要 arithmetic 迁移到 MXU 后，kernel 的速度得到提升。然而，profiling 表明，仅靠 MXU execution 并不能得到高效的 KDA 实现。

这项优化改变了 bottleneck。

此前被昂贵 arithmetic 掩盖的 operations，如今占据了 execution time 的很大一部分。

我们观察到四类主要的 residual overhead。

第一，computation 在结构上仍然 fragmented，导致重复的 intermediate processing，并限制了 reuse。

第二，多个 kernel boundaries 要求 intermediate tensors 被 materialized，并在不同 stages 之间传输。

第三，mathematical formulation 偏好的 layout 并不总是与后续 MXU operations 所需的 layout 一致。Concatenation、transpose、reshape 和 relayout operations 可能消耗 faster GEMMs 所带来的很大一部分收益。

第四，一些 matrix operations 会形成 dependent chains。串行执行这些 operations 时，没有足够的 independent work 来隐藏 MXU startup 和 pipeline latency。

我们按逐开关消融差值对这四类 overhead 定量：每类的占比 = 修复它的那个优化 在 MXU-port 基础上消去的时间。每个数字都对应一个可复现的 A/B 测量。对于 代表性 workload（headline 固定形状 S=8192(4×2048 packed), H=16），MXU-port 实现 14.73 ms 的时间分布为：

18%（2.62 ms）actual matrix computation（全部优化后的残余即为计算本体），

24%（3.56 ms）layout transformation / 寻址（gather-scatter 与非对齐布局，由统一寻址消去），

20%（2.94 ms）intermediate materialization / kernel boundaries（4-stage 间的中间张量写读，由融合消去），

38%（5.61 ms）pipeline stalls / 空转步（grid 编排税 ~1.1 µs/步 × O(N·H·NC) 步 + 依赖链气泡，由平铺 grid 与交错消去）。

其中第四类有独立佐证：flat-grid 前每 grid 步实测固定成本 ~1.1 µs；交错前 per-(head,chunk) 依赖链延迟呈 ~1 µs 不变量（见 §6.6 三形态对照）。

因此，后续优化的重点是 matrix operations 周围的 kernel，而非 matrix operations 本身。

# 6. 阶段 2：重构 KDA Kernel

这一阶段不是修改 KDA 的数学定义，而是重新安排同一批 computation 的生产者、 消费者和数据布局。阶段 1 已经把 K3 Kimi Kernel 专用的 safe_gate 计算搬到 MXU； 这里继续解决 MXU 周围的 HBM 往返、layout conversion 和无效调度。普通 KDA （包括 Kimi-Linear）始终使用 safe_gate=False，不能开启 K3 专用路径。

重构前，forward 被拆成四个 kernel：

gate activation + chunk cumsum
    → HBM(g_cumsum)
    → intra-chunk
    → HBM(w, u, kg, Aqk, ...)
    → chunk recurrence
    → HBM(h, v_new)
    → output

重构后，同一计算变成两个 kernel：

gate activation + chunk cumsum + intra-chunk
    → HBM(g_cumsum, w, u, kg, Aqk, ...)
    → chunk recurrence + output
    → HBM(o, final_state)

下面逐项解释每次 transformation 在代码和 tensor shape 上具体改变了什么。

## 6.1 把 gate activation 和 chunk cumsum 融入 intra-chunk kernel

原路径先在完整 token 轴上计算 gate activation 和 chunk cumsum，写出结果后， intra-chunk 再按 chunk 收集同一批数据：

# Before: 两个独立 kernel
g_act = activate_gate(g, A_log, dt_bias)
# [1, aligned_tokens, num_heads, key_dim]
g_cumsum = chunk_cumsum(g_act)
# [1, aligned_tokens, num_heads, key_dim]

g_cumsum_chunks = gather_by_chunk(g_cumsum)
# [num_chunks, chunk_size, num_heads, key_dim]
w, u, kg, Aqk = intra_chunk(g_cumsum_chunks, q, k, v)

intra-chunk 本来就以一个 head、一个 chunk 为计算单位，因此可以在已经读入的 g_block 上直接完成前两步：

# After: 一个 fused kernel；下列值都留在当前 kernel instance 内
g_block = activate_gate(g_block, A_log[head], dt_bias[head])
# [chunk_size, key_dim]
g_cumsum_block = hillis_steele_scan(g_block)
# [chunk_size, key_dim]

w, u, kg, Aqk = intra_chunk_math(
    g_cumsum_block, q_block, k_block, v_block
)
# w, kg: [chunk_size, key_dim]
# u:     [chunk_size, value_dim]
# Aqk:   [chunk_size, chunk_size]

Pallas TPU 不能直接把 jnp.cumsum lowering 成设备指令，因此这里使用 log2(chunk_size) 轮“右移后相加”的 Hillis–Steele scan。它删除的是独立的 chunk_cumsum kernel，以及 cumsum 与 intra-chunk 之间的 gather/scatter 和 HBM round trip；数学上仍然是相同的 chunk 内 inclusive prefix sum。为了供第二个 fused kernel 使用并保持既有 API，g_cumsum 仍可作为第一个 fused kernel 的 output 写出一次；被删除的是“先写出、再读回给 intra-chunk”的中间边界。

现有的约 0.08 ms 是 fusion 之后在 kernel 内分别关闭 gate activation 和 scan 得到的 stage ablation，不是独立 chunk_cumsum kernel 在同 shape、同协议下的 fusion 前耗时，因此这里不把 0.08 ms 写成 before/after speedup。两次 fusion 的 完整端到端收益统一在 §6.3 报告。

## 6.2 合并 chunk recurrence 与 output

第二次 fusion 的关键不是“少调用一次 kernel”这么简单，而是 output 和 state update 恰好消费同一组短生命周期中间量。进入 chunk c 时：

  • S_c [key_dim, value_dim] 是 entry state，只包含之前所有 chunk 的信息；
  • u_c / w_c / kg_c / Aqk_c 是第一个 fused kernel 产生的 chunk-local 中间量；
  • h_c 是处理当前 chunk 之前的 S_c snapshot。

一个 chunk 的计算依赖如下：

h_c = S_c
# [key_dim, value_dim]

v_new_c = u_c - w_c @ h_c
# [chunk_size, value_dim]

o_c = inter_chunk_output(q_c, g_c, h_c) + Aqk_c @ v_new_c
# [chunk_size, value_dim]

S_next = decay(h_c) + kg_c.T @ v_new_c
# [key_dim, value_dim]

o_c 必须读取 entry state h_c，不能先更新 state 再计算 output。当前 chunk 的 causal contribution 已经由 Aqk_c @ v_new_c 负责；如果这里改读 S_next，当前 chunk 会被计算两次。由此也能看出，o_c 和 S_next 共享完全相同的上游输入 h_c 与 v_new_c，而这两个值在当前 chunk 用完后没有其他消费者。

原实现让两个 kernel 通过 HBM 交接这两个中间量：

# Before: recurrence kernel
h_c = S                                            # [key_dim, value_dim]
v_new_c = u[c] - w[c] @ h_c                        # [chunk_size, value_dim]
S_next = decay(h_c) + kg[c].T @ v_new_c             # [key_dim, value_dim]

HBM_h[c] = h_c                                     # write HBM
HBM_v_new[c] = v_new_c                             # write HBM
S = S_next                                          # 留给下一个 chunk

# Before: output kernel
h_c = HBM_h[c]                                     # read HBM
v_new_c = HBM_v_new[c]                             # read HBM
o[c] = output(q[c], g[c], h_c, v_new_c, Aqk[c])

fusion 后，同一套变量直接在一个 kernel 内流向两个消费者：

# After: fused recurrence + output kernel
h_c = S                                            # [key_dim, value_dim], VMEM
v_new_c = u[c] - w[c] @ h_c                        # [chunk_size, value_dim], VMEM

o_c = output(q[c], g[c], h_c, v_new_c, Aqk[c])     # [chunk_size, value_dim]
S_next = decay(h_c) + kg[c].T @ v_new_c             # [key_dim, value_dim]

o[c] = o_c                                          # write HBM
S = S_next                                          # VMEM，供下一个 chunk 使用

因此，优化前后的核心差别是：

Before: S → recurrence → HBM(h, v_new) → output → o
After:  S → recurrence + output（h, v_new 留在 VMEM）→ o, S_next

h / v_new 不再是 kernel output；最终只写出完整的 o 和每条序列末尾的 final_state [key_dim, value_dim]。在 PR4 的独立对照 workload 中，后两个阶段从 7.75 ms 降到 5.29 ms；完整 kernel 的 HBM traffic 从 4.18 GB 降到 1.63 GB。 后者还包含其他阶段的 layout conversion，不能误解为 h / v_new 自身就占 2.55 GB。

## 6.3 Fusion 的整体结果

两次 fusion 共同把四个 kernel boundary 减为两个，并删除推理不需要的 backward intermediates；例如 fused RHS 从 320 列缩到 256 列，o 也不再经过 fp32 intermediate materialization。headline 形状上，fuse 档将延迟从 14.73 ms 降到 11.79 ms，贡献 1.25×。这是一项完整档位的端到端结果，不能拆分为 两个未经同协议测量的单项 speedup。

正确性上，fused recurrence + output 与旧路径逐位一致；gate scan 则随完整 forward 一起通过 fp32 naive reference、ablation 组合与 32K varlen 测试。

## 6.4 统一两个 kernel 之间的 layout 和寻址

fusion 之后，剩余两个 kernel 仍使用不同的 tensor arrangement。原实现通过 chunk_indices[c] = (seq_id, local_chunk_id) gather 每个 chunk，kernel 结束后 再 scatter 回 token layout；下一阶段又重复同样的过程。

但 _align_seqs(..., align=chunk_size) 已经把每条序列分别补到 chunk_size 的 整数倍，再按原顺序连接。若第 i 条序列对齐后有 n_i 个 chunk，则：

aligned_cu_seqlens[i] = chunk_size * sum(n_j, j < i)
start = aligned_cu_seqlens[seq_id] + local_chunk_id * chunk_size
chunk_id = sum(n_j, j < seq_id) + local_chunk_id

所以 start = chunk_id * chunk_size

例如原始长度为 [70, 130]、chunk_size=64：

对齐后长度         = [128, 192]
aligned_cu_seqlens = [0, 128, 320]
chunk_indices      = [(0,0), (0,1), (1,0), (1,1), (1,2)]
由 indices 得到 start = [0, 64, 128, 192, 256]
直接用 chunk_id*64  = [0, 64, 128, 192, 256]

两种寻址完全相同。原 gather 没有重新排序，也没有跳过 token；它只是把本来已经 连续且顺序正确的数据，复制到另一个相同顺序的数组中。用同一套变量写成伪代码：

# Before: 每个 kernel 前后转换 layout
x_token_layout = x
# [1, aligned_tokens, num_heads, feature_dim]
x_chunks = gather(x_token_layout, chunk_indices)
# [num_chunks, chunk_size, num_heads, feature_dim]
x_kernel = x_chunks.transpose(2, 0, 1, 3).reshape(
    1, num_heads, num_chunks * chunk_size, feature_dim
)
# [1, num_heads, aligned_tokens, feature_dim]

x_block = x_kernel[:, head:head+1,
                   chunk_id*chunk_size:(chunk_id+1)*chunk_size, :]
y_block = kernel(x_block)

y_kernel[:, head:head+1,
         chunk_id*chunk_size:(chunk_id+1)*chunk_size, :] = y_block
y_token_layout = scatter(
    restore_chunk_axis(y_kernel), chunk_indices
)
# [1, aligned_tokens, num_heads, feature_dim]
# 下一个 kernel 再次 gather(y_token_layout, chunk_indices)


# After: transpose 一次；两个 kernel 直接共享同一 layout
x_token_layout = x
# [1, aligned_tokens, num_heads, feature_dim]
x_kernel = x_token_layout.transpose(0, 2, 1, 3)
# [1, num_heads, aligned_tokens, feature_dim]

x_block = x_kernel[:, head:head+1,
                   chunk_id*chunk_size:(chunk_id+1)*chunk_size, :]
y_block = kernel(x_block)

y_kernel[:, head:head+1,
         chunk_id*chunk_size:(chunk_id+1)*chunk_size, :] = y_block
# y_kernel 直接传给下一个 kernel；不再 scatter 后重新 gather

对应的 Pallas BlockSpec 很直接：完整数组为 [1, num_heads, aligned_tokens, feature_dim]，每个 program 读取 [1, 1, chunk_size, feature_dim]，位置只由 head 和 chunk_id 决定。

这项改动删除 gather×5、scatter×6、chunk_indices、第二个 kernel 入口处的 transpose 和 HBM 中的 fp32 副本。headline 形状上，unified_layout 将延迟从 11.79 ms 降到 8.23 ms，贡献 1.43×；新旧 layout 逐元素差异严格为 0。

## 6.5 执行网格只遍历实际存在的 chunk

旧 grid 是 (num_sequences, num_heads, max_chunks_per_sequence)。每条短序列都要 扫描 batch 内最长序列的 chunk 数；越界 program 虽然不产生结果，仍消耗 grid step 和 DMA 编排成本：

# Before: grid=(num_sequences, num_heads, max_chunks_per_sequence)
for sequence, head, local_chunk in grid(
    num_sequences, num_heads, max_chunks_per_sequence
):
    if local_chunk < chunks_in_sequence[sequence]:
        S[sequence, head] = step(
            S[sequence, head], chunk(sequence, local_chunk)
        )

统一 layout 后，所有有效 chunk 已按原序列顺序 packed 在连续 token 轴上，因此 grid 可以直接遍历实际 num_chunks：

# After: grid=(num_heads, num_chunks)
for head, chunk_id in grid(num_heads, num_chunks):
    if start_flag[chunk_id]:
        S = initial_state[seq_id[chunk_id], head]

    o[chunk_id], S = step(S, chunk[chunk_id])

    if end_flag[chunk_id]:
        final_state[seq_id[chunk_id], head] = S

seq_id / start_flag / end_flag 的长度都等于实际 chunk 总数。它们分别标记 chunk 所属序列、何时加载 entry state、何时写回 final_state。跨 chunk recurrence 的 串行 dependency 没有被移除，arithmetic count 也没有改变；新 grid 只是删除了 不存在的 (sequence, head, local_chunk) program 和旧路径的 trash-bin chunk。

headline 形状上，grid step 从 N×H×NT_max 降为 H×NC_total，延迟从 8.23 ms 降到 5.02 ms，贡献 1.64×。ShareGPT 分布包含更多短序列，空转比例 更高，因此这项调度优化在真实 varlen workload 上通常收益更大。新旧路径在精确 cu_seqlens 和空序列输入上逐元素差异严格为 0。

## 6.6 Head-block Pipelining and Interleaving

一些 KDA stages 包含 dependent matrix operations 的 chains。naive implementation 会先为一个 head 或 block 执行完整 dependency chain，然后才开始另一个 independent work。

这会导致 instruction-level parallelism 不足，并可能使 MXU pipeline 部分 idle。

因此，我们改为 interleave independent chains。

从概念上看：

Original:
head 0: op1 → op2 → op3 → ...
head 1: op1 → op2 → op3 → ...

Interleaved:
head 0: op1
head 1: op1
head 2: op1
...
head 0: op2
head 1: op2
...

每条 chain 内的 mathematical dependencies 保持不变，而 independent chains 会在原本暴露 latency 的位置提供有用工作。

我们用三形态对照实验分离收益机制。同一数学、三种执行形态（headline 形状）：

形态延迟
head 由 grid 维迭代（每步单 head，依赖链串行暴露）5.02 ms
kernel 内 for h 串行（省 grid 编排税，链仍串行）4.12 ms
跨 head 交错（stage-major 发射 + 跨 H 向量化 elementwise）2.62 ms

分离出两个机制：grid→kernel 内的 0.90 ms 是编排税（TPU 单核 grid 只做 DMA 双缓冲，无计算-计算重叠）；串行→交错的 1.50 ms 是 MXU 依赖链气泡的填充—— 交错前每 (head, chunk) 的小 GEMM 依赖链呈 ~1 µs/单元的延迟不变量（fill/drain 无法被同链后继隐藏），交错后相邻 head 的独立 dot 填入气泡，µs/step 从 16.1 降到 10.2。跨 H 向量化同时把 elementwise 指令数 ÷H。

head_block 还让 kernel 直接消费模型原生的 [1, T, H, D] layout，消除五个输入 张量各一次全量 transpose；headline 形状上的 HBM traffic 从 1.52 GB 降到 1.14 GB。该 layout 收益和跨 head interleaving 由同一开关共同兑现。

Measured contribution：head_block+interleave 合计 1.91×（5.02→2.62 ms）。

[要求：结合 generated code/XProf 验证这一解释。量化收益究竟来自 reduced MXU bubbles、overlap、instruction scheduling，还是其他 mechanism。] 🟡 部分满足（上文三形态对照把收益分离为编排税 0.90 ms + 依赖链气泡 1.50 ms）；generated code 级验证 ⏳ 未做。

# 14. Lessons

优化 TPU 上的 Kimi K3 后，我们得出了若干经验。

第一，algorithm-level hardware friendliness 并不会自动转化为 system-level efficiency。Kimi K3 暴露了规则的 matrix computation，但 software stack 仍需将这些 computation 显式映射到 MXU。

第二，加速 dominant arithmetic 会改变 bottleneck。一旦 matrix computation 足够快，tensor layout、materialization、kernel boundaries 和 scheduling 就会成为一阶问题。

第三，应将 matrix accelerator utilization 视为 end-to-end dataflow 问题。如果构造 operands 需要昂贵的 layout transformation，那么更快的 GEMM 所能提供的价值就会十分有限。

最后，小型 dependent matrix operations 所需的 scheduling decisions 不同于传统 large-GEMM optimization。Independent KDA heads 和 blocks 提供了 interleave work 的机会，可以隐藏原本会暴露的 pipeline latency。

# 15. 结论

Kimi K3 提供了一种在 numerical 层面兼容 BF16 chunk computation、在结构上适合 matrix accelerators 的 KDA formulation。然而，现有 TPU path 并未充分利用这一机会。

我们首先将 matrix-based FlashKDA computation strategy 移植到 TPU，把主要 KDA prefill computation 从 vector-oriented execution 转向 MXU matrix operations，并获得 2.28×（固定形状）/ 2.48×（ShareGPT-derived 分布）speedup。

对该实现进行 profiling 后，我们发现 computation structure、kernel boundaries、tensor layout 和 execution scheduling 中出现了一组新的 bottlenecks。通过 structural optimization、kernel fusion、layout optimization 和 pipelining 解决这些 bottlenecks 后，又进一步获得 5.6×（固定形状累计）的 improvement。

在已实测的 Kimi K3 prefill workloads（headline 固定形状与 ShareGPT-derived varlen 分布批）上，最终实现相较于原始 SGLang-JAX 实现达到 12.8×（固定形状）/ 18.4×（ShareGPT-derived 分布）speedup。cached prefix 不构成 kernel 评估维度（KDA 递归 state 定长，见 §1），评估空间为 S × B。

[最终要求：完整的 56-point fixed-length benchmark matrix（8 S × 7 B × 3 实现）与 7 个 ShareGPT-distributed B configurations（每个 replay 100 个 sampled lengths）可用后，将“最高达到”的表述替换为两类 workloads 各自的 geometric-mean/range 结果。headline 应同时包含 typical 和 maximum performance。]

# 附录 A：Chunk Size（BT）的选择

BT=64 经扫描确定（数据：aug-12-learn/sweep_*.json）。更大的 BT（128/256）虽然 摊薄每 chunk 的固定成本，但 chunk 内三角求解的工作量 ∝ BT²（Neumann 因子链的 [BT,BT] 小 GEMM 规模与级数深度同时上升），且 VMEM 工作集随 BT² 增长挤压双缓冲； 实测 BT=64 全面优于 128。这与 FlashKDA 在 GPU 上选 C=16 不冲突：C=16 服务的是 fp16 数值范围与 SM 占用，TPU/bf16 下 MXU 友好的块尺寸是 64/128 量级，数值安全性 由 §4 的指数预算（子块 SB=16 保持不变）单独保证。

# 附录 B：VMEM 边界与 head-block 的适用条件

head-block 模式（kernel 一次消费全部 H 个 head）的 VMEM 工作集 ∝ H。实测边界： H=16, K=V=128 时非 safe_gate 路径（每 head 独立衰减张量共 16 份展开）需 45.13 MB，超过 v6e 的 32 MB scoped VMEM 上限，编译期 OOM；safe_gate 路径 （strip-GEMM 共享子块结构）同形状工作集 ~5 MB。因此 head_block 生效条件为 fuse ∧ safe_gate ∧ H % 8 == 0（TPU 块布局要求次末维为 8 的倍数）， 不满足时自动回退非 hb 路径（数值不变，见 §13 逐位一致性）。该边界由 生产形状（H=16/K=128）的失败案例发现——小形状单测不会触发， 已固化为 kernel 内的静态断言与开关约束（commit 98920a41）。
